# run-limits — лимиты внутри процесса

Слово юзера (26.09): «лимиты должны быть встроены в сам процесс а не быть частью команды вызова».
Точка входа, подключившая библиотеку первым действием (пролог ниже), ставит себе пределы сама при любом способе вызова: голым `bash x.sh`, из cron, из другого скрипта, из агента.

Файлы: `runlimits.py` (ядро: супервизор `--wrap`, `enter`, `run_child`, `max_parallel`, `pool`), `runlimits.sh` (половина для bash), `runlimits.mjs` (половина для node), `census-guard.py` (сторож ценза) и его списки `entrypoints-declared.txt`, `census-exclude.txt`, `census-allowlist.txt`, `runlimits-teeth.sh` + `mutations.tsv` + `mutate.sh` (зубы и мутации). Только stdlib python3, совместимость с 3.9.

## Профили

Таблица `PROFILES` в `runlimits.py` — единственный дом чисел. Переопределения переменными окружения нет. Зуб T12 пинит дайджест таблицы: правка числа — это правка таблицы и пина в зубах.

| профиль | для чего | mem_mb | runtime_s | max_parallel linux | max_parallel darwin |
|---|---|---|---|---|---|
| `unit` | один прогон `claude plugin test` / `node --test` / `bun test` / pytest | 6144 | 900 | 4 | 1 |
| `mutation` | один прогон мутанта | 6144 | 180 | 4 | 1 |
| `model-session` | один `claude -p` (pressure, судья) | 3072 | 1800 | 8 | 4 |
| `runner` | оркестратор: раннер мутаций, стенд, *-teeth, *-bench, run-all, гейтер | 2048 | 7200 | — | — |
| `pipeline` | `claude-patch-all.sh`, `sweep.sh`, `run-from-snapshot.sh` | 12288 darwin / 16384 linux | 5400 | — | — |

- `mem_mb` — предел суммы памяти дерева процессов под этим супервизором: на Linux — RSS, на darwin — `max(rss, phys_footprint)` каждого процесса (п. 3, R1). Поддеревья вложенных супервизоров в сумму не входят.
- `runtime_s` — стенное время от старта супервизора (`Supervisor.__init__`): время всего вызова, подготовка и запуск scope входят (FIX14 R3).
- `max_parallel` есть только у листовых профилей; для `runner` и `pipeline` `max_parallel()` бросает `ValueError`.

Основания чисел:
- Машины: мак 24 GiB (`hw.memsize` 25 769 803 776 Б), 12 ядер, без свопа; usbox 187 GiB (`free -m` 191 810 MiB), 32 ядра, без свопа.
- Повод: 26.09 01:47 kernel panic мака — четыре параллельных `claude plugin test` мутационного раннера выросли до 18/42/40 GiB.
- `unit` / `mutation` 6144: замер test-warden, один `claude plugin test` статус-мода на маке — пик суммы RSS дерева 2644 МБ при пике одного процесса 457 МБ (`Catalyst-programs/2026-09-26-claude-limit-agent-death/logs-warden/norm-peak.json`, поле `peak_scope_sum_mb`). Библиотека меряет сумму дерева; при 4096 запас был бы всего 1,5×, при 6144 — 2,3×.
- `mutation` 180 с и 4 параллельно: раннер мутаций #509 — 4 параллельно × 180 с.
- darwin `max_parallel` 1 для листовых: 4 × 6144 МБ уже больше, чем мак переживает рядом с рабочей сессией.
- `pipeline` 5400 с: конвейер патча — максимум ~31 мин на маке, ~19 мин на usbox (замеры в `CENSUS-ENTRYPOINTS.md` программы `2026-09-26-claude-limit-agent-death`).
- Для сравнения: порог P1 test-warden на один процесс — 4096 МБ.

Бюджет раннера по построению: `runner.mem_mb + max_parallel(leaf) × leaf.mem_mb`. Например, раннер мутаций на usbox: 2048 + 4 × 6144 = 26 624 МБ; на маке: 2048 + 1 × 6144 = 8192 МБ.

## Коды выхода

| код | значит |
|---|---|
| 86 | предел памяти: сторож (сумма RSS дерева) или, на Linux, ядро (oom-kill в scope прогона) |
| 87 | предел времени: сторож (стенное время) или, на Linux, ядро (`RuntimeMaxSec` scope, `Result=timeout`) |
| 88 | пределы недоступны: на Linux нет `systemd-run` / user-менеджера / scope не подтверждён, на darwin не читается `phys_footprint` своего процесса, отказ `ps`, неизвестный профиль |
| 89 | пролог не нашёл библиотеку |
| 143 | родитель супервизора ушёл, дерево убито |
| прочие | код ребёнка как есть; ребёнок убит сигналом N → 128+N. Сигнал, полученный самим супервизором (TERM/INT/HUP), код не меняет: в журнале поле `signal`, `limit` сигналом не выставляется: сигнал сам `limit` не выставляет и не сбрасывает; при пределе, сработавшем во время остановки, `limit` — этот предел, а основание остановки — в `during_stop`; в stderr строка `stopped: signal` (ниже); ребёнок, сам вышедший кодом 143, поля `signal` не даёт |

Строки в stderr, всегда одной строкой:
- `RUNLIMITS: <label> killed: mem <peak> MB > <cap> MB (profile <p>)` — сторож; в журнале `limit=mem`, `by=watchdog`. На Linux остановка сторожа на тике, где счётчик `oom_kill` scope вырос с прошлого тика, — итог ядра: строка ядра ниже (по коду ребёнка после остановки), `by=kernel` (FIX14 R1, зуб T106).
- `RUNLIMITS: <label> killed: mem (kernel oom-kill) > <cap> MB (profile <p>)` — только Linux: ядро убило по `MemoryMax` самого ребёнка (признак ниже; ребёнок умер от SIGKILL); код 86, в журнале `limit=mem`, `by=kernel`, `oom_victim=unattributed` (A9: ядро имени жертвы не называет), `child_exit=137`.
- `RUNLIMITS: <label> killed: mem (kernel oom-kill of a descendant; child exit <c>) > <cap> MB (profile <p>)` — только Linux: ядро убило другой процесс scope, ребёнок вышел сам с кодом `<c>`. Всё равно 86: предел достигнут в дереве прогона, его результат недоверенный (fail-closed). В журнале `limit=mem`, `by=kernel`, `oom_victim=descendant`, `child_exit=<c>`.
- `RUNLIMITS: <label> killed: SIGKILL not sent by the supervisor, cause unverified (<причина>)` — ребёнок умер от SIGKILL, который супервизор не посылал, а причина не доказана: признак не прочитан (причина — почему), прочитан и отрицателен (внешний `kill -9`), или darwin (признака нет). Источник, который не доказан, строка не называет. Код 137 как есть, в журнале `limit=unverified`.
- `RUNLIMITS: <label> killed: time <dur> s > <cap> s (profile <p>)` — сторож; в журнале `limit=time`, `by=watchdog`.
- `RUNLIMITS: <label> killed: time (kernel RuntimeMaxSec) > <runtime_s+30> s (profile <p>)` — только Linux: systemd остановил scope по `RuntimeMaxSec` (`Result=timeout`); код 87, в журнале `limit=time`, `by=kernel`, `child_exit`.
- `RUNLIMITS: <label> killed: parent gone (set RUNLIMITS_DETACH=1 to detach)` — код 143, в журнале `limit=parent-gone`.
- `RUNLIMITS: <label> stopped: signal <ИМЯ> from outside` — супервизор сам получил сигнал (`TERM` / `INT` / `HUP`; первый, если их было несколько; в том числе пересланный внешним супервизором вложенному); код ребёнка как есть, в журнале поле `signal=<ИМЯ>`, `limit` не меняется (FIX14c R3, зубы T118, T119; предел и сигнал вместе — FIX14d R3, зуб T120).
- `RUNLIMITS: <label> killed: mem <n> MB > <cap> MB during the stop, nested supervisors not spared (profile <p>)` / `… killed: time <t> s > <cap> s during the stop, …` — сторож во время щажения вложенных (п. 6b; в остановке по памяти вместо них `killed: mem <n> MB > <cap> MB, then <m> MB during the stop, nested supervisors not spared (profile <p>)`); код 86 / 87, в журнале `limit=mem` / `time`, `by=watchdog`, `during_stop`, `stop_kill=sparing`.
- `RUNLIMITS: <label> killed: mem <n> MB > <cap> MB during the stop window (profile <p>)` — тик сторожа в окне остановки не по памяти (п. 6c); код 86, в журнале `limit=mem`, `by=watchdog`, `during_stop`, `stop_kill=window`.
- `RUNLIMITS: <label> killed: mem <n> MB > <cap> MB, then grew more than 10% over <b> MB to <m> MB during the stop window (profile <p>)` — остановка по памяти, оборванная тиком окна (п. 6c): одно событие — одна строка, вместо строки `killed: mem <n> MB > <cap> MB (profile <p>)`; код 86, в журнале `limit=mem`, `by=watchdog`, `during_stop=mem`, `stop_kill=window-growth`.
- `RUNLIMITS: <label>: cannot measure during the stop (<ошибка>); nested supervisors not spared` — одна на проход щажения (пп. 6b, 6d).
- `RUNLIMITS: <label> refused: <причина>`

## Пролог: как точка входа подключается

Каждая точка входа ищет библиотеку сама, первым действием, без внешней настройки:
1. `RUNLIMITS_HOME`, если задан (тогда только он; нет там `runlimits.py` → 89).
2. Иначе подъём от физического каталога самого скрипта: на каждом предке `A` — `A/tools/run-limits/runlimits.py`, затем `A/Catalyst/tools/run-limits/runlimits.py`. Это покрывает `Catalyst` (R), `Catalyst-CC-Patch` (K → `../Catalyst/...`), `Catalyst-programs` (G), снимок прогона (`$snap/Catalyst-CC-Patch` → `$snap/Catalyst`; `snapshot-kit.sh` копирует оба дерева без `.git`/`node_modules`/`__pycache__`) и копии на usbox, где рядом лежит `Catalyst/`.
3. Не нашёл → `RUNLIMITS: <скрипт> refused: library not found (searched: <список>)`, код 89. Запуска без пределов нет.

Первая строка каждого пролога — маркер `RUNLIMITS-PROLOGUE v1 profile=<p>`; по нему считает сторож ценза (первые 40 строк файла). В фазе B `@PROFILE@` заменяется профилем точки входа (в маркере и в вызове). Тексты ниже — канон: зубы T4–T8 и T11 вырезают их отсюда между маркерами и исполняют.

### bash

Сразу после shebang (`#!/usr/bin/env bash`); только bash (нужны `BASH_SOURCE` и `source`), не `sh`.

<!-- prologue:bash:begin -->
```bash
# RUNLIMITS-PROLOGUE v1 profile=@PROFILE@
_rl=${RUNLIMITS_HOME:-}; _rls=$_rl; _rld=
if [ -z "$_rl" ]; then _rld=$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd -P); fi
while [ -n "$_rld" ] && [ -z "$_rl" ]; do
    for _rlc in "$_rld/tools/run-limits" "$_rld/Catalyst/tools/run-limits"; do _rls="$_rls $_rlc"
        if [ -z "$_rl" ] && [ -f "$_rlc/runlimits.py" ]; then _rl=$_rlc; fi; done
    _rlp=$(dirname "$_rld"); if [ "$_rlp" = "$_rld" ]; then break; fi; _rld=$_rlp; done
if [ -z "$_rl" ] || [ ! -f "$_rl/runlimits.py" ]; then
    echo "RUNLIMITS: $0 refused: library not found (searched: ${_rls# })" >&2; exit 89; fi
source "$_rl/runlimits.sh"; runlimits_enter @PROFILE@ "$@"
```
<!-- prologue:bash:end -->

`runlimits_enter`, если процесс ещё не под супервизором: `exec python3 runlimits.py --wrap <p> --label <скрипт> -- "$BASH" <скрипт> "$@"`; путь скрипта — `${BASH_SOURCE[1]}` вызывающего. `exec` сохраняет pid: вызывающий видит тот же процесс. Пролог написан без `&&`-цепочек на верхнем уровне, чтобы работать под `set -euo pipefail`.

### python

После docstring и `from __future__` (если есть), до остальных импортов.

<!-- prologue:python:begin -->
```python
# RUNLIMITS-PROLOGUE v1 profile=@PROFILE@
import os, sys
_rl_h = os.environ.get("RUNLIMITS_HOME") or None; _rl_s = [_rl_h] if _rl_h else []
_rl_d = None if _rl_h else os.path.dirname(os.path.realpath(__file__))
while _rl_d and not _rl_h:
    _rl_s += [os.path.join(_rl_d, "tools", "run-limits"), os.path.join(_rl_d, "Catalyst", "tools", "run-limits")]
    _rl_h = next((c for c in _rl_s[-2:] if os.path.isfile(os.path.join(c, "runlimits.py"))), None)
    _rl_d = None if os.path.dirname(_rl_d) == _rl_d else os.path.dirname(_rl_d)
if not _rl_h or not os.path.isfile(os.path.join(_rl_h, "runlimits.py")):
    sys.stderr.write("RUNLIMITS: %s refused: library not found (searched: %s)\n" % (sys.argv[0], " ".join(_rl_s))); sys.exit(89)
sys.path.insert(0, _rl_h); import runlimits; runlimits.enter("@PROFILE@")
```
<!-- prologue:python:end -->

`enter()`, если не активен: `os.execv(sys.executable, [sys.executable, runlimits.py, "--wrap", p, "--label", argv0, "--", sys.executable, ...])`, где хвост — `sys.orig_argv[1:]` на 3.10+ (сохраняет `-m`, `-c`, `-u` и флаги интерпретатора) и `sys.argv` на 3.9.

### node (.mjs)

Первыми строками модуля. Ограничение ESM: статические `import` модуля исполняются ДО тела модуля, то есть до пролога; точка входа с тяжёлыми побочными эффектами при импорте переводит их на динамический `import()` после пролога.

<!-- prologue:node:begin -->
```js
// RUNLIMITS-PROLOGUE v1 profile=@PROFILE@
import { existsSync as _rlE, realpathSync as _rlR } from 'node:fs';
import { dirname as _rlD, join as _rlJ } from 'node:path';
import { fileURLToPath as _rlF, pathToFileURL as _rlU } from 'node:url';
let _rlH = process.env.RUNLIMITS_HOME || null; const _rlS = _rlH ? [_rlH] : [];
for (let d = _rlH ? null : _rlD(_rlR(_rlF(import.meta.url))); d && !_rlH; d = _rlD(d) === d ? null : _rlD(d))
  for (const c of [_rlJ(d, 'tools', 'run-limits'), _rlJ(d, 'Catalyst', 'tools', 'run-limits')]) { _rlS.push(c); if (!_rlH && _rlE(_rlJ(c, 'runlimits.py'))) _rlH = c; }
if (!_rlH || !_rlE(_rlJ(_rlH, 'runlimits.py'))) {
  process.stderr.write(`RUNLIMITS: ${process.argv[1]} refused: library not found (searched: ${_rlS.join(' ')})\n`); process.exit(89); }
await (await import(_rlU(_rlJ(_rlH, 'runlimits.mjs')).href)).enter('@PROFILE@');
```
<!-- prologue:node:end -->

`enter()`, если не активен: `spawn('python3', [runlimits.py, '--wrap', p, '--label', argv1, '--', process.execPath, ...process.execArgv, ...process.argv.slice(1)], {stdio:'inherit'})`, ждёт его выхода, затем `process.exit(status ?? 128 + signo)`. `execArgv` сохраняет флаги node (`--test`, `--max-old-space-size`). Исходный node остаётся родителем супервизора; SIGINT/SIGTERM/SIGHUP, пришедшие ему, передаются супервизору (без этого node умирал бы от сигнала, а супервизор узнавал бы об этом только как «родитель ушёл»).

## Маркер активности и вложенность

- Супервизор кладёт ребёнку `RUNLIMITS_ACTIVE=<pid супервизора>:<profile>`, `RUNLIMITS_DEPTH=<n>` и `RUNLIMITS_REGISTRY=<реестр, где лежит его метка>` (п. 6a) — всегда, так что потомок с другим `TMPDIR` видит метки предков. Зуб T46.
- `enter()` считает процесс уже ограниченным, только если pid из маркера — ПРЕДОК (цепочка ppid) и этот предок опубликовал метку супервизора (п. 6a); argv не доказывает ничего. Утёкший маркер (демон, скопированный `env`) даёт новую обёртку, а не пропуск. Зубы T8, T43.
- `enter()` при живом маркере ничего не делает: вложенный вход живёт в бюджете родителя. Исключение — профиль (A13, E2): запрошенный профиль с меньшим `mem_mb` или меньшим `runtime_s`, чем у активного, получает свою обёртку (активный его не покрывает); неизвестное имя активного профиля — тоже своя обёртка. Зубы T72, T73, T88, T89.
- `run_child()` / `runlimits_child` / `runChild()` всегда запускают НОВЫЙ супервизор со своим пределом. На Linux он получает свой scope (sibling-юнит, из cgroup родителя выходит). Сторож родителя на обеих площадках, обходя дерево для суммы RSS, не спускается в поддерево вложенного супервизора, опознанного по его метке (п. 6a); argv `runlimits.py --wrap` без метки считается в сумму (для kill дерево берётся целиком). Зуб T42 (Linux).
- `pool(profile)` = `ThreadPoolExecutor(max_workers=max_parallel(profile))`. `run_child` не принимает `max_workers`: параллельность задаёт только библиотека.
- `RUNLIMITS_DEPTH` ≥ 16 → отказ 88: страховка от бесконечной переобёртки, если проверка предка когда-нибудь перестанет узнавать свой супервизор.

## Супервизор `--wrap`

`python3 runlimits.py --wrap <profile> [--label <имя>] -- <argv…>`

1. Профиль известен (иначе 88), `ps` читается до старта (иначе 88, ребёнок не запускается). darwin: `phys_footprint` своего pid читается до старта (`proc_pid_rusage`, R1); не читается (нет библиотеки, символа, ошибка вызова) → `refused: darwin memory measure unavailable: <причина>`, 88, ребёнок не запускается — как отказ Linux без systemd (п. 2). Зуб T101.
2. **Linux.** Нет `systemd-run` в PATH, нет `systemctl`, или `systemctl --user is-system-running` не `running`/`degraded` → 88. Иначе ребёнок идёт под `systemd-run --user --scope --quiet --unit runlimits-<pid>-s<start> -p MemoryMax=<mem_mb>M -p MemorySwapMax=0 -p RuntimeMaxSec=<runtime_s+30> -- /bin/sh -c <шим> <файл> <argv>`. Без `--collect`: упавший scope (`Result=oom-kill`) остаётся загруженным, пока супервизор не прочитает его `Result`; затем супервизор сам собирает его `systemctl --user reset-failed`. Успешный scope systemd собирает сам. Имя scope и каталога шима (он же метка, `runlimits-<pid>-s<start>-*` в реестре, п. 6a) несут pid супервизора и время его старта (`ps -o lstart=` при `LC_ALL=C`, секунды эпохи; A2): при старте супервизор снимает (`reset-failed`, удаление каталога) упавшие scope и каталоги шима тех супервизоров, чьего процесса с этим pid и этим временем старта уже нет (убит SIGKILL до сборки). Остатки живых супервизоров не трогаются — они ещё прочитают свой `Result`. Имена другой формы (до этой версии) не трогаются: владельца по ним не определить. Активные scope мёртвых владельцев (их процессы ещё живы) не трогаются. Шим пишет `/proc/self/cgroup` в файл подтверждения и ждёт, пока супервизор его удалит; супервизор проверяет, что cgroup ребёнка — именно этот scope и что `memory.max` / `memory.swap.max` равны заказанным, и только тогда отпускает шим в `exec` команды. Любое расхождение → дерево убивается, 88; команда не стартует без ядерного предела (фальшивый `systemd-run`, который исполняет команду без scope, ловится этой проверкой — зуб T13c).
3. **Обе площадки — сторож.** Раз в 0,5 с снимок `ps -axo pid=,ppid=,pgid=,rss=,stat=,lstart=,command=`, дерево потомков ребёнка по ppid, сумма памяти. Память процесса на Linux — `rss`; на darwin — `max(rss, phys_footprint)`: колонка `rss` не видит страниц в компрессоре и в swap, и под давлением памяти растущее дерево не пересекало бы предел (замер 27.09: пик 1051,7 МБ по `rss` при пределе 3072 МБ и компрессоре 12,7 GiB); `phys_footprint` («Память» монитора активности) их включает. Читается `proc_pid_rusage(pid, RUSAGE_INFO_V2)` из `libproc`; pid ушёл между снимком и чтением (`ESRCH`) — 0 в этом тике (зуб T113); иная ошибка или исключение Python из самого вызова ctypes (FIX14 R10, текст `proc_pid_rusage(<pid>) raised: …`; при старте то же исключение — отказ 88, зуб T114) — берётся `rss`, pid идёт в поле журнала `footprint_unread`, первая такая за прогон — строка `RUNLIMITS: <label>: phys_footprint unread for <pid>: <errno или текст>; rss used` (зуб T112). `EPERM` — процесс чужого uid без прав: его память на darwin не измерить, других источников нет; недосчёт — граница с именем (п. 8), не принятый дефект. Та же сумма судит окна остановки и щажение (6b, 6c); поле `peak_rss_mb` журнала — её пик (имя поля прежнее). Зуб T100. Больше `mem_mb` → 86; стенное время больше `runtime_s` → 87. Kill: SIGTERM дереву, через 5 с — SIGKILL оставшимся (на Linux ещё `cgroup.kill` своего scope). Перед каждым сигналом дерево снимается заново: сигнал получают текущие потомки (связь по ppid доказана свежим снимком) и запомненные процессы, выпавшие из дерева (сироты), только если их время старта не изменилось (иначе pid переиспользован; A2). Сумма RSS тика — объединение без повторов текущего дерева ребёнка и деревьев запомненных живых pid с тем же start; поддеревья вложенных супервизоров исключаются в обеих частях (A1, E1, зуб T90). Отказ `ps` посреди прогона → остановка без измерителя `ps` (E3), 88: повторных вызовов `ps` нет. На Linux при читаемом `/proc` вид остановки строится по ppid из всех процессов своего uid (`/proc/<pid>/stat`), включая sibling-scope вложенных; члены своего scope из `cgroup.procs` добавляются к дереву. Отказ открытия `/proc` — `PsError`, как отказ `ps`; ошибка stat отдельной записи пропускается; SIGTERM дереву, SIGKILL нагрузкам через `GRACE_S`, щажение вложенных и ловушки — по 6a/6d, затем `cgroup.kill`. Если `/proc` тоже недоступен, SIGTERM и SIGKILL идут своему несобранному ребёнку; у профиля `runner` SIGKILL и `cgroup.kill` ждут выхода ребёнка не дольше SIGTERM + `NESTED_STOP_S`, у остальных — `GRACE_S`. На darwin SIGTERM ребёнку и его группе, SIGKILL им же через `GRACE_S`. На darwin запомненные потомки вне ребёнка без измерителя не отличить от переиспользованных pid: им сигнал не посылается, строка `RUNLIMITS: <label>: remembered descendants not signalled: cannot measure (<why>): <pids>`, в журнале `unverified_pids`, метка остаётся в реестре с файлом `unverified`: строки `<pid> <start>` этих процессов (start — из запомненного дерева; не прочитанный снимком start пишется `-`, FIX14 R5; запись атомарная, временный файл + `os.replace`, как `stopped`). Следующая уборка с работающим измерителем (п. 6a) шлёт им SIGKILL. Зубы T60, T110.
4. **Сигналы.** SIGINT/SIGTERM/SIGHUP супервизору передаются всему дереву. После SIGTERM/SIGHUP через 5 с — SIGKILL оставшимся, в том числе потомкам, пережившим самого ребёнка; исключения — вложенные супервизоры с предками (п. 6a) и ловушка раннера (профиль `runner`, п. 6d). Код ребёнка возвращается как есть; запись журнала несёт поле `signal` с именем первого полученного сигнала (`TERM` / `INT` / `HUP`), `limit` сигналом не выставляется: сигнал сам `limit` не выставляет и не сбрасывает; при пределе, сработавшем во время остановки, `limit` — этот предел, а основание остановки — в `during_stop`; в stderr одна строка `RUNLIMITS: <label> stopped: signal <ИМЯ> from outside` (при сработавшем пределе — и его строка `killed: …`). Без сигнала супервизору поля нет: ребёнок, сам вышедший кодом 143, от внешнего TERM отличим (зубы T118, T119, T120).
5. **Родитель ушёл.** Супервизор на обеих площадках следит за своим родителем: `ppid` сменился → дерево ребёнка SIGTERM, через 5 с SIGKILL (исключения те же: пп. 6a, 6d), строка `killed: parent gone (set RUNLIMITS_DETACH=1 to detach)`, код 143, в журнале `limit=parent-gone`. Явный детач: `RUNLIMITS_DETACH=1` в окружении точки входа (`RUNLIMITS_DETACH=1 nohup x.sh &`) выключает слежение за родителем у этого супервизора; пределы памяти и времени остаются, в журнале `detached=true`. Ручка действует только на супервизор, который её увидел: из окружения ребёнка она убирается, вложенные супервизоры следят за своими родителями.
6. **Выжившие.** После выхода ребёнка (любого: сам, по сигналу, по пределу) супервизор завершает всё, что осталось от его дерева: SIGTERM, через 5 с SIGKILL; число таких процессов — поле журнала `survivors_killed`. Кандидаты: накопленная память дерева — записи всех тиков, чьи pid живы в последнем снимке с тем же временем старта, плюс текущий снимок (запись выбывает, только когда её pid исчез из снимка или сменил start, то есть переиспользован; A2; констрейт FIX9: снимок в окне смерти ребёнка держит только зомби-корня — перезапись стирала бы перепривязанных потомков из sweep, T41e, зуб T49); на Linux — ещё все процессы scope прогона (`cgroup.procs`, в конце `cgroup.kill`); на darwin — ещё члены группы процессов ребёнка (ребёнок стартует в своей группе, `setpgrp`; группа не считается своей, если pid ребёнка уже занят другим процессом). darwin: процесс, ушедший и из группы, и из дерева (двойной fork + `setsid`), находится по токену `RUNLIMITS_TREE=<mark>` в окружении (A15); граница — в перечне ниже (E16). На Linux его находит scope. Отказ скана окружения в уборке — строка `RUNLIMITS: <label>: descendant scan unavailable (<why>); leftovers not verified` всегда; итог `limit=unverified` с `env_scan` в журнале — когда этот отказ случился и иной предел не сработал, как бы ни завершился ребёнок (сам, по сигналу, переданному супервизором); прогон, уже получивший итог по пределу, уходу родителя или признаку ядра, сохраняет его (E5, FIX14 R13, зуб T92).
6a. **Вложенный супервизор не режется посреди своей остановки.** Во всех трёх местах SIGKILL (эскалация после SIGTERM/SIGHUP, остановка по пределу или уходу родителя, добивание выживших) вложенный супервизор и его дерево не получают SIGKILL, пока не выйдут сами, но не дольше `NESTED_STOP_S` = 2·`GRACE_S` + `UNIT_SETTLE_S` + 5 = 20 с от SIGTERM; `cgroup.kill` — после них. SIGKILL посреди его остановки оставил бы каталог шима, unit и запись журнала несделанными. Вложенный супервизор опознаётся по метке, которую публикует он сам: каталог `runlimits-<pid>-s<start>-*` в реестре, где start совпадает с живым временем старта pid; argv не доказывает ничего. Реестр — `RUNLIMITS_REGISTRY`, если задан, иначе временный каталог процесса (`tempfile.gettempdir()`). Одно правило для обеих веток (FIX9, FIX10): абсолютный путь, существует, каталог, владелец — текущий uid или root (A5), доступный на запись группе или остальным — только со sticky-битом (общий `/tmp`); симлинк проходит, только если им владеет root или текущий uid, — тогда проверяется и возвращается (и передаётся ребёнку) разрешённый каталог. Констрейнт: на darwin без `TMPDIR` умолчание — `/tmp`, симлинк root на `/private/tmp`; отказ по любому симлинку отказал бы каждой обёрнутой точке входа, запущенной без `TMPDIR` (T56); симлинк чужого uid в общем каталоге не разворачивается (T55). Умолчание проверяется тем же правилом, непроверенного каталога нет. Метка в реестре засчитывается и снимается только как своя: `lstat` — каталог (не симлинк) uid читателя; имя чужого uid или симлинк в общем каталоге меткой не считаются. Супервизор публикует метку в свой реестр и передаёт его ребёнку, читатели (`--is-active`, щажение, учёт памяти, снятие остатков) смотрят в реестр из своего окружения. Констрейнт: не в `gettempdir()` каждого читателя — потомок с другим `TMPDIR` не видел бы метку предка (T36). Негодный реестр → отказ 88 строкой `refused: RUNLIMITS_REGISTRY <путь>: <причина>` (умолчание — `<путь> (from gettempdir()): <причина>`), тихого возврата к временному каталогу нет; в `--is-active` негодный реестр = не активен (обёртка затем откажет той же строкой). Зубы T44, T45, T49–T56. Метку супервизор публикует на обеих площадках (на darwin это пустой каталог, шима там нет); start — `ps -o lstart=` при `LC_ALL=C`, секунды эпохи на обеих площадках (A2; точность 1 с). Время старта своего pid не читается → отказ, 88; каталог метки не создаётся → отказ, 88. Щадятся и предки вложенного супервизора внутри ожидаемого (процесс, который ждёт его, например раннер с ловушкой EXIT): в том же окне `NESTED_STOP_S` и после выхода самого вложенного — их уборка идёт после ожидания; тот же сторож 6b. Зубы T47, T48. При старте метки мёртвых владельцев снимаются на обеих площадках (упавшие scope — только Linux). Перед снятием метки уборщик шлёт SIGCONT процессам из её `stopped` (E4) и SIGKILL процессам из её `unverified` (R6) — каждому, только пока его pid жив с записанным start; иной start или нет pid — пропуск (pid переиспользован, процесс не наш); файл снимается вместе с меткой. Файл не читается — метка остаётся до следующей уборки. Записи `unverified` (FIX14 R5, R6, R8, зубы T109, T110): pid нет — запись снимается; start иной — запись снимается как чужая, сигнала нет; start pid в снимке не прочитан — запись остаётся, сигнала нет; start записан `-` — SIGKILL, только если pid несёт токен окружения этого прогона (`RUNLIMITS_TREE=runlimits-<pid>-s<start>` из имени метки, скан A15), иначе запись остаётся и строка `RUNLIMITS: <label>: <pid> left unverified by a dead supervisor kept: start not recorded, <причина>`; SIGKILL отказан (`EPERM` и иной `OSError`) — запись остаётся со строкой `… SIGKILL to <pid> left unverified by a dead supervisor failed: …`. Оставшиеся записи переписываются в файл атомарно; метка живёт, пока в файле есть записи. Уборка идёт трижды: при старте (зуб T103 (a)), в остановке (A12, зуб T71) и на выходе (A12, зуб T103 (b)). Снимок недоступен (`ps`, а на Linux своего scope также `/proc`) → вложенных щадить некого, SIGKILL сразу (хост ловушки раннера на Linux — п. 6d). Граница доверия: метку может опубликовать любой процесс того же пользователя (каталог в реестре со своим pid и временем старта) — процессы того же пользователя лежат внутри домена доверия супервизора; метка отличает супервизор от совпавшего argv, не от намеренной подделки. Зубы T37, T39 (Linux), T40 (darwin).
6b. **Сторож жив во время щажения.** Каждые `TICK_S` щажения — тик сторожа по всему, чего ещё ждём (деревья вложенных включены: на darwin за ними нет ядерного предела). Сумма RSS больше `mem_mb` → SIGKILL всему сразу, вложенным тоже, строка `killed: mem <n> MB > <cap> MB during the stop, nested supervisors not spared (profile <p>)`, код 86; стенное время больше `runtime_s` (если остановка началась не по времени) → то же со строкой `killed: time <t> s > <cap> s during the stop, …`, код 87. Журнал: `limit` / `by=watchdog` этого предела и `during_stop` = предел, по которому шла остановка (`null` — по сигналу). Ручки `RUNLIMITS_TEST_NO_MEM_WATCH` / `RUNLIMITS_TEST_NO_TIME_WATCH` действуют и здесь. Снимок недоступен во время щажения (`ps`, а на Linux своего scope также `/proc`) → строка `cannot measure during the stop (…); nested supervisors not spared` (одна на проход щажения), SIGKILL сразу; хост ловушки раннера и её процессы на Linux щадятся дальше (п. 6d). Журнал `stop_kill=sparing`. Остановка по памяти, оборванная этим сторожем: одна строка `killed: mem <n> MB > <cap> MB, then <m> MB during the stop, nested supervisors not spared (profile <p>)` вместо двух (T38c). Констрейнт: во время остановки предел внешнего ограничивает всё его дерево, вложенные супервизоры с их деревьями включены (их собственные пределы тоже в силе). Зуб T38 (Linux).
6c. **Сторож жив в окне остановки.** В каждом 5-секундном окне между SIGTERM и SIGKILL (остановка по пределу или уходу родителя, эскалация после SIGTERM/SIGHUP — и пока ребёнок жив, и после его выхода, добивание выживших) — тик сторожа каждые `TICK_S` по всему, чего ещё ждём, вложенные включены. Остановка не по памяти (время, сигнал, уход родителя, добивание после выхода ребёнка): сумма RSS больше `mem_mb` → SIGKILL всему сразу, строка `killed: mem <n> MB > <cap> MB during the stop window (profile <p>)`, журнал `stop_kill=window`. Остановка по памяти: окно SIGTERM сохраняется, но сумма RSS больше `WINDOW_GROWTH` = 1,10 от суммы в начале остановки → SIGKILL всему сразу, одна строка `killed: mem <n> MB > <cap> MB, then grew more than 10% over <b> MB to <m> MB during the stop window (profile <p>)` вместо строки остановки, журнал `stop_kill=window-growth`; добивание выживших после такой остановки меряется от той же суммы начала остановки. Код 86, `limit=mem`, `by=watchdog`, `during_stop` = предел, по которому шла остановка (`null` — сигнал или добивание после обычного выхода). Из пределов, сработавших во время остановки, в `limit` остаётся первый (`stop_limit = stop_limit or …`, `runlimits.py:744/751/815/821`); предел, по которому шла остановка, — в `during_stop` (`finish`, `runlimits.py:590–593`). `RUNLIMITS_TEST_NO_MEM_WATCH` выключает и этот тик; Нет снимка (`ps`, а на Linux своего scope также `/proc`) в окне → окно идёт до своего SIGKILL. Зуб T41 (Linux); T38 растит память после окна эскалации, чтобы проверять щажение, а не окно.
6d. **Ловушка раннера доживает до конца своей уборки (#552).** Только профиль `runner` — оркестратор с ловушкой EXIT, которой контракт раннеров обещает бюджет `STOP_S` (раздел «Зубы и мутации», «Сигнал раннеру»); листовые профили (`unit`, `mutation`, `model-session`) и `pipeline` не меняются: SIGKILL через `GRACE_S` (зуб T15). В эскалации после SIGTERM/SIGHUP и в остановке по пределу или уходу родителя, пока ребёнок жив, SIGKILL не получают: сам ребёнок (хост ловушки) и процессы, рождённые после первого сигнала остановки дереву, у которых вся цепочка ppid до ребёнка идёт только через щадимые pid (ребёнок, предки вложенных п. 6a, такие же новорождённые) — `kill_tree`, его `ps`, `rm` ловушки. Первый сигнал остановки (D8) — что раньше: пересланный супервизором INT / TERM / HUP (`forward_pending`; ловушка раннера стартует и на INT, до всякого TERM) или SIGTERM остановки по пределу или уходу родителя (`terminate`); цели и их start снимаются в этот момент один раз. Рождённый после — pid вне набора целей первого сигнала (вместе с деревом, запомненным последним тиком) или тот же pid с другим start; start, не прочитанный с любой стороны, — «существовал». Всё, что существовало при первом сигнале (нагрузки), получает SIGKILL через `GRACE_S` после SIGTERM, как прежде, кроме деревьев вложенных и их предков (п. 6a); потомок нагрузки, рождённый после первого сигнала, не щадится — его родитель не щадим (зуб T125). Окно — до SIGTERM + `NESTED_STOP_S`, то же, что у вложенных; выход ребёнка (ловушка закончена) снимает щажение сразу, затем `cgroup.kill`; конец окна — SIGKILL всему (зуб T126). Сторож 6b тикает без изменений: предел памяти или времени снимает всё щажение сразу. Отказ `ps` на Linux с подтверждённым scope: вид `/proc` сохраняет идентичности pid, распознавание вложенных, `trap_own` и SIGKILL нагрузкам через `GRACE_S` (T130). `start` этого вида — `btime + starttime // SC_CLK_TCK`, в секундах эпохи как `ps lstart` (T129); `comm` режется по последней `)`. Если `/proc` тоже недоступен, вложенные не щадятся; хост ловушки и его новорождённые щадятся до конца окна под ядерными `MemoryMax` и `RuntimeMaxSec` scope: в измеряемой остановке без снимка запомненные проверяются `/proc` → членство в своём scope → одиночный ps (кроме E3); новорождённые без снимка не достигаются до `cgroup_kill` конца окна — без дерева помощники ловушки неотличимы, и `recheck` их не видит, а ребёнок исключается из посылки по pid (T123; T123s — канал один: одиночный ps; T123b — одиночный ps тоже падает, остаётся членство scope). darwin: отказ `ps` снимает щажение ловушки — ядерного предела нет, без замера памяти дерево на маке не держится; граница одной площадки. Остановка без измерителя `ps` (E3, `stop_unmeasured`): на Linux с читаемым `/proc` первый SIGTERM фиксирует `born_ref`, затем действует общий цикл щажения; нагрузки получают SIGKILL через `GRACE_S`, ловушка заканчивает уборку (T131), повторных вызовов `ps` нет. Когда `/proc` тоже недоступен, действует D7: SIGKILL по pid и `cgroup.kill` ждут выхода ребёнка не дольше SIGTERM + `NESTED_STOP_S`; новорождённые без снимка не видны, SIGKILL по pid идёт одному ребёнку, нагрузки до `cgroup.kill` его не получают. Этот путь держат ядерные пределы scope; T127 проверяет завершение уборки при самостоятельно уходящей нагрузке, T132 — SIGKILL не уходящему хосту в окне `[NESTED_STOP_S, NESTED_STOP_S + 2)` от TERM. Darwin — без изменений: SIGKILL через `GRACE_S`. Зубы T121 (уход родителя), T122 (TERM супервизору), T123 (Linux, отказ `ps`), T124 (вложенный вышел раньше `GRACE_S`), T125, T126, T127 (Linux, остановка без измерителя), T128 (INT, затем TERM: `kill_tree`, начатый после INT, не убит); листовой профиль — T15.
7. **Терминал и job control (darwin).** Своя группа ребёнка стала бы фоновой для управляющего терминала: чтение терминала остановило бы ребёнка (SIGTTIN). Поэтому, если супервизор держит терминал (его группа — передняя), на время жизни ребёнка передней становится группа ребёнка; Ctrl-C приходит группе ребёнка напрямую. Остановку ребёнка (Ctrl-Z, SIGTTIN) супервизор видит (`waitid` с `WSTOPPED`): терминал возвращается группе супервизора (если его держит группа ребёнка), группа супервизора останавливается SIGTSTP, как передняя задача, — оболочка видит задачу остановленной. На SIGCONT (`fg` / `bg`) группа ребёнка снова получает терминал, только если группа супервизора передняя (`fg`), и получает SIGCONT. После выхода ребёнка терминал возвращается, только если его держит группа ребёнка (после `bg` он у оболочки). Стенное время остановки входит в `runtime_s`. Потомок текущего дерева (дерево ребёнка этого вызова), чей start снимок не прочитал, перечитывается поштучно (`proc_start`); прочитан — он останавливается и записывается в `stopped` как все; не прочитан — строка `RUNLIMITS: <label>: descendant <pid> not held: start unreadable`, и он не останавливается: без start его нельзя записать в `stopped`, а незаписанный остановленный процесс некому продолжить (R7, зуб T104). Запомненный pid без start вне текущего дерева не перечитывается и не останавливается: он мог умереть, а pid — достаться чужому процессу, чей новый start присвоил бы его (FIX14 R7, зуб T111); он называется строкой `RUNLIMITS: <label>: remembered <pid> not held: outside the tree, start not recorded` — одной на pid за прогон (FIX14b, зуб T117). Граница с именем: pid дерева, умерший и переиспользованный между снимком текущего дерева и поштучным чтением, неотличим.
8. **Запись о прогоне** — одна JSONL-строка на прогон (включая отказы) в `~/.local/state/run-limits/runs.jsonl`; каталог переопределяется `RUNLIMITS_LOG_DIR`. Поля: `time`, `host`, `profile`, `label`, `argv` (первые 300 символов), `peak_rss_mb`, `duration_s`, `exit`, `limit` (`mem` / `time` / `parent-gone` / `unverified` / `unavailable` / `null`), `by` (`watchdog` / `kernel` / `null`), `survivors_killed`, `detached`; если супервизор сам получил сигнал (п. 4) — `signal` (`TERM` / `INT` / `HUP`); если сторож убил дерево во время остановки (щажение вложенных, п. 6b, или окно SIGTERM, п. 6c) — `during_stop` (предел, по которому шла остановка, или `null`) и `stop_kill` (`sparing` / `window` / `window-growth`); при убийстве ядром ещё `child_exit` (код ребёнка) и для памяти `oom_victim` (`unattributed` / `descendant`; A9); darwin — `footprint_unread` (pid, чей `phys_footprint` не прочитан, R1), если такие были. Граница с именем: у pid с `EPERM` (чужой uid без прав) память берётся по `rss`, сжатые и выгруженные страницы не видны; недосчёт виден в этом поле и строке stderr. Граница с именем (скан A15): `ps -E` не печатает окружение платформенных бинарей Apple (`/bin/sleep`), поэтому остаток — платформенный бинарь Apple с токеном — остаётся, не убивается; дерево запуска убивается группой раньше, в скан уходят только переродители. Цена тика на darwin: вызов `proc_pid_rusage` на учтённый pid, до двух вызовов на pid за тик при эскалации (тик окна остановки меряет те же pid ещё раз). Ротация при 5 МБ → `.1`. Отказ записи — одна строка в stderr, прогон не падает.

### Linux: `MemoryMax` равен `mem_mb`

Замер 26.09 на usbox (systemd 257, cgroup v2, контроллер `memory` делегирован user-менеджеру): scope с `MemoryMax=150M`, аллокатор до 300 МБ, опрос `ps` раз в 0,5 с. Резкий аллокатор: ребёнок убит OOM за 0,51 с, `ps` успел увидеть 6 МБ. Постепенный (5 МБ / 50 мс): убит за 1,53 с, `ps` видел максимум 108 МБ. systemd: `Failed with result 'oom-kill'`, `150M memory peak`. RSS и заряд cgroup — разные величины: RSS считает и тёплые файловые страницы (уже в page cache), которые cgroup этому процессу не заряжает (замер 27.09 на usbox: 148 МБ RSS против 144 МБ `memory.current`), и разделяемые страницы (copy-on-write после fork — зуб T1b). Поэтому при `MemoryMax = mem_mb` победитель не определён: обе защиты останавливают дерево в пределах лимита, атрибуция — по тому, кто действовал: ядро, если счётчик `oom_kill` вырос на тике остановки или признак ядра найден после выхода ребёнка, иначе сторож (FIX14 R1, зубы T1, T106). Сторож на Linux срабатывает ещё по времени (у ядра запас `+30 с`).

Признак ядерного предела (после выхода ребёнка, до добивания выживших):
1. `oom_kill` в `memory.events` scope, пока его cgroup существует (читается и на каждом тике сторожа — счётчик растёт монотонно), больше 0 → убийство по памяти;
2. `Result` юнита (`systemctl --user show <unit>.scope`, ждать до 5 с, пока юнит не станет `inactive`/`failed`): `oom-kill` → убийство по памяти; `timeout` → остановка по `RuntimeMaxSec`; юнит собран (`LoadState=not-found`) → он не упал, предел не срабатывал.
Память → 86 (строка ребёнка или потомка, выше); время → 87 `killed: time (kernel RuntimeMaxSec)`. Признак не прочитан (ошибка `systemctl`, юнит не устоялся) или отрицателен, а ребёнок умер от чужого SIGKILL → 137 со строкой `killed: SIGKILL not sent by the supervisor, cause unverified (<причина>)`.

## Почему не `ulimit`

- На darwin `RLIMIT_AS` / `RLIMIT_DATA` ядром не применяются: `ulimit -v` на маке ничего не ограничивает.
- bun/JSC резервируют огромное виртуальное адресное пространство: `ulimit -v` на Linux ломает их на старте, задолго до реального роста памяти.
- `RLIMIT_*` — на процесс, а не на дерево: четыре ребёнка по пределу вместе уходят за него вчетверо.

## Сторож ценза `census-guard.py`

`python3 census-guard.py [--root <дерево>]… [--allowlist <файл>] [--declared <файл>] [--exclude <файл>] [--list]`

Сторож сам — точка входа с прологом (профиль `unit`).

- Корни по умолчанию: R (`../..` от этого каталога), K = `R/../Catalyst-CC-Patch`, G = `R/../Catalyst-programs`. Без `--root` сторож берёт и три списка рядом с собой (`census-allowlist.txt`, `entrypoints-declared.txt`, `census-exclude.txt`; нет файла → отказ 2); с явным `--root` — только списки, названные флагами. Пропускаются `.git`, `node_modules`, `__pycache__`, симлинки, `*.md`; файл скриптового вида больше 8 МиБ, не закрытый glob-ом исключений, — нарушение `VIOLATION <path>: <n> B > <max> B, not scanned (exclude it with a reason or split it)` (C3; строки `SKIPPED` нет).
- Точка входа — файл (`.sh .bash .zsh .py .mjs .js .cjs .ts .mts .cts .tsx`, либо без расширения с shebang sh/bash/zsh/python/node/bun), чей исполняемый код порождает листовую форму или запускает другую точку входа. Исполняемый код = без комментариев; в python ещё без голых строк-выражений (docstring); файлы `*.md` не читаются.
- Листовые формы: `plugin test`; `claude … -p` (голова — слово `claude` или переменная `$CLAUDE`, `$CLAUDE_BIN|_EXE|_CMD|_CLI|_PATH|_IMAGE`); `node … --test` (голова `node`, `$NODE`, `process.execPath`); `bun test`; `vitest`; `jest`; `pytest` (не строка `import`); `systemd-run`. Команда может продолжаться до 3 следующих строк, только если строка кончается на `\`, `(`, `[` или `,`.
- Запуск другой точки входа (та же команда = строка плюс предшествующие строки-продолжения):
  - sh: скрипт — слово команды, или первый операнд после слова-интерпретатора (`bash`/`sh`/`zsh`/`dash`, `python*`, `node`, `bun`, `$…PY…`/`$…NODE…`/`$…BASH…`/`$…BUN…`, `exec`, `source`, `.`); `-` (скрипт из stdin) вызовом не считается;
  - python/js: в команде есть API порождения (`subprocess.*`, `Popen`, `os.system`/`os.exec*`/`os.spawn*`, `spawn`/`spawnSync`, `execFile*`, `execSync`, `check_call`/`check_output`, `run_one`, `sys.executable`, `process.execPath`) или интерпретатор в кавычках; путь после `-` не считается;
  - исполнение кода в своём процессе: js `import … from '<x.mjs>'` / `import('<x.mjs>')`; python `import m` / `from m import …` / `from . import m`, если рядом со скриптом лежит `m.py`.
- Имя цели разрешается по совпадению хвоста пути, затем по ближайшему каталогу; при равенстве засчитываются все кандидаты. Замыкание — до неподвижной точки.
- Маркер засчитывается только отдельной строкой-комментарием (`#` или `//`) с профилем `[A-Za-z0-9_-]+` в первых 40 строках; текст маркера внутри строкового литерала прологом не считается.
- Чего сторож не видит по построению: интерпретатор или бинарь в переменной с иным именем (`"$IMAGE" -p`, `bun "$BENCH"`, `run_one "$s" bash "$s"`), python-импорт не соседнего модуля, корни конвейеров, чьё дерево не порождает ни одной листовой формы (например, `claude-patch-all.sh`: `bun "$BENCH"`, бенчи, `*-teeth.sh`). Такие корни называются явно в `entrypoints-declared.txt`.
- Во всех трёх списках относительный путь или glob — от каталога файла-списка; пустые строки и строки с `#` пропускаются.
- Allowlist (`census-allowlist.txt`): строки `<путь>\t<основание>`. Строка без основания → отказ 2. Там `runlimits.py`: сам супервизор, обернуть себя нельзя.
- Объявленные точки входа (`entrypoints-declared.txt`): строки `<путь>\t<профиль>\t<основание>` — корни профилей `pipeline`/`runner` из `CENSUS-ENTRYPOINTS.md` программы `2026-09-26-claude-limit-agent-death`, которых сторож не находит по формам. Судятся наравне с найденными (маркер или allowlist). Объявленного пути нет на диске → `VIOLATION <список>:<n>: stale declaration <path> (no such file)`, выход 1. Строка без профиля или основания → отказ 2.
- Исключённые копии (`census-exclude.txt`): строки `<glob>\t<основание>`, `**` — любая глубина, glob каталога кончается на `/`. Копия несёт пролог своего оригинала; судится оригинал. Точки входа внутри совпавшего каталога (или совпавшие файлы) не судятся и считаются; каталог копий, не названный в списке, судится как обычно. Glob без совпадений → `VIOLATION <список>:<n>: stale exclusion <glob> (matches nothing)`; объявленный путь под исключением → `VIOLATION <список>:<n>: exclusion hides declared entry <path> (<glob>)` (он всё равно судится); выход 1. Строка без основания → отказ 2.
- Выход: 0 — у каждой судимой точки входа маркер в первых 40 строках или строка allowlist и ни одной протухшей строки списков; 1 — строки `VIOLATION …`; 2 — отказ прибора (нечитаемый корень, пустой список деревьев, битый или отсутствующий список, нечитаемый файл).
- `--list` печатает `ENTRY <path>:<line> profile=<p|NONE> form=<форма>` для судимых (объявленные — `form=declared <профиль> (<список>:<n>)`) и `EXCLUDED <path>:<line> form=<форма> glob=<glob>` для исключённых — ценз для фазы B.
- Итоговая строка всегда: `census-guard: <N> entry points (<F> by form, <D> declared), <M> with prologue, <K> allowlisted, <X> excluded, <V> violations`; N — судимые (объединение найденных по формам и объявленных), X — исключённые точки входа, V — нарушения точек входа плюс протухшие строки списков.

## Зубы и мутации

Оба раннера без явного scope ничего не запускают: `--scope <имя>[,<имя>…]` — только перечисление имён; слова «всё», шаблонов и `*` нет, полный прогон = перечисление всех имён. Без `--scope` или с неизвестным именем (в том числе `all`) — код 2 и строка `nothing run: scope required (--scope <name>[,<name>...]); known: <имена>`, ни одного запуска. `--list` печатает известные имена и ничего не запускает.

- `bash runlimits-teeth.sh --scope <зуб>[,…]` — имена T1–T146, T1b, T123s и T123b. T1b/T13/T14/T31/T32/T34/T37/T38/T39/T41/T42/T49/T50/T58/T59/T66/T67/T68/T71/T106/T115/T123/T123s/T123b/T127/T129/T130/T131/T132/T140/T141/T143/T144/T146 только Linux (T120, T128, T133–T139, T142 и T145 — на обеих площадках), T33/T40/T56/T61/T75/T91/T92/T97/T100/T101/T110/T112/T113/T114 только darwin: названные на другой площадке, печатают именованный `SKIP` и не входят в счёт; части зубов, возможные только на одной площадке — T11(b), T24(b) Linux, T26(d) darwin, — печатают именованный sub-skip строкой `SUBSKIP <зуб>: <причина>` (T26(c) идёт на обеих: на darwin беглеца с `setsid` находит токен A15); итог `TEETH platform=<p> scope=<имена> ran=… passed=… failed=… expected=… subskips=N`, где expected — число названных зубов этой площадки, N — число под-скипов; выход 0 только при ran = passed = expected. `EXPECTED_TEETH` пинит число известных зубов площадки (darwin 115, linux 135): расхождение со списком имён — FATAL, код 2. Отказ `sublog` (п. E11) печатает строку `FAIL <зуб> sublog: …` в stderr; внутри подоболочки `$(sublog …)`, где счётчик `FAILED` умирает вместе с ней, он ещё дописывает строку в `$TMP/subfails`; итог `failed` = свой счёт + число строк файла (R8, зуб T105). Прямой вызов `sublog … || …` в оболочке раннера файл не пишет: его отказ валит свой зуб, и он считается один раз (FIX14 R12, зуб T115). `--each-alone` гоняет каждый названный зуб этой площадки отдельным вызовом раннера `--scope <зуб>`: строки `alone <зуб> | …` (вывод вызова), `alone PASS|FAIL <зуб>`, итог `alone ran=N passed=P failed=F` и `alone failed: <имена>|none`, выход 0 только при passed = ran = expected. Каждый зуб строит свои фикстуры сам и проходит без других зубов перед ним (FIX14b, зуб T116: T65 строил свою ссылку из фикстуры T64). T81 сверяет число строк `SUBSKIP` с `subskips=` на scope с под-скипом этой площадки (darwin T24, linux T26); без наблюдённого под-скипа — `FAIL T81 instrument: …` (сравнение 0 = 0 ничего не доказывает). Повтор `--scope` накапливает имена, `--scope=` равен `--scope`; разбор scope идёт с выключенным глоббингом (`set -f`), `*` не раскрывается; если после отбора платформы не осталось ни одного зуба — код 2 и строка `nothing run on <p>: every scoped tooth is <other>-only`. Зубы входят через свой пролог с профилем `runner`; `RL_UNDER_TEST` подменяет проверяемую библиотеку; `RL_TEETH_UNDER_TEST` / `RL_MUTATE_UNDER_TEST` — проверяемые раннеры для T29 / T30 / T35 / T36. Таймаут вызова внутри зуба (`bounded`) бьёт по всему дереву вызова: SIGTERM всем (раннер убирает свой временный каталог), через `BGRACE` = `STOP_S` + 5 с SIGKILL оставшимся; только верхний pid оставил бы дерево работать без присмотра.
- Сигнал раннеру (оба раннера): `trap` на INT (130), HUP (129), TERM (143) и EXIT. Уборка на выходе: SIGTERM всему дереву раннера; ожидание фактического выхода каждого процесса этого снимка (вместе с осиротевшими) не дольше `STOP_S` = 2·`GRACE_S` + `UNIT_SETTLE_S` + 5 с (полная остановка супервизора — эскалация, добивание выживших, состояние scope — плюс запас; числа читаются из `runlimits.py`), SIGKILL оставшимся, затем удаление временного каталога. Остановка короче `STOP_S` оставила бы каталог шима и unit убитого супервизора до следующего старта. Супервизор раннера (профиль `runner`) даёт этой ловушке окно `NESTED_STOP_S` = `STOP_S` от SIGTERM: через `GRACE_S` SIGKILL получают нагрузки, но не хост ловушки и не рождённые ею `kill_tree` и `rm` (п. 6d, зубы T121–T126); сами ловушки не меняются. Bash исполняет ловушку только после конца foreground-команды или substitution; без ловушки он в окне substitution умирает по сигналу, а в простом foreground-ожидании игнорирует INT. T35 судит сырой wait-status (`exited:<код>` / `signaled:<номер>`), потому что `$?` bash-родителя сворачивает оба исхода в 128+N. Долгие ожидания — фоновые задачи с `wait` (`bounded` в зубах, прогоны зубов в `mutate.sh`). Фоновая задача неинтерактивного bash стартует с игнорируемым SIGINT, а игнорируемый при входе сигнал bash не перехватывает: ловушка INT зубов под `mutate.sh` не действует, их убирает SIGTERM уборки `mutate.sh`. Зубы T35 (сигнал) и T36 (ожидание выхода супервизоров).

Строки чужой площадки и строки, чьи зубы все только чужой площадки (по `--list` раннера зубов), печатаются `SKIP` (второй вид называет зубы) и не считаются (FIX14 R11, зуб T108). - отказ `ps` во время щажения: Linux использует вид `/proc` (T130); если он тоже недоступен, хост и его новорождённые щадятся до конца окна под ядерными пределами scope (T123); darwin — щажение снимается (граница площадки, ядерного предела нет);
- `kill_tree` в раннере мутаций, уборке зубов и фикстуре сверяет start первого снимка перед финальным SIGKILL; свежие потомки доказываются связью ppid (T133, T134, T135). `bounded` и `kill12` сохраняют start вместе с pid; при смене или непрочитанном start сигнал не посылается, причина пишется в лог кейса; `bounded` не блокируется на живом ребёнке: после ожидания по идентичности ребёнок, который всё ещё жив (отказ сигнала, недостоверное чтение идентичности — свой непожатый ребёнок не может быть заменён), получает BRC 124 без `wait` (T138, M197);
- отказ ожидания супервизора в `trap_case` возвращает 1 до блокирующего `wait` (T136): супервизор, живущий дольше окна ловушки с запасом, — предметный провал `trap window unbounded: …` с добиванием своего pid (M168); `instrument: …` остаётся только за не стартовавшим случаем без отказа предмета — не стартовавший с собственным отказом предмета (маркер `refuse_line`, runlimits.py:505, `RUNLIMITS: <label> refused: …`) даёт предметную форму `subject refused at start: …`, отказ вложенного супервизора (метка `<label>n`) — `inner supervisor refused at start: …`; строка отказа выбирается по точной метке с позиции 1, чужая метка не засчитывается (T145, M198–M200; M174/M183 краснеют предметно); отказ ожидания pid новорождённого — такой же отказ до последующих ожиданий (T137). Ряды мутаций: 207, включая M173–M186 и M195–M200; D7 зелёный на базе, красный под M178/M179; Linux `proc_start` читает только `/proc`, без повторного `ps` после отказа измерителя — окно None-ветки не содержит одиночного ps (M182, T140); `recheck` после потерянной меры не консультирует одиночный ps (M186, T146);
- `RUNLIMITS_TEST_PROC_UNREADABLE=1` отказывает всему виду `/proc` после публикации метки супервизора (собственный start для метки читается без ручки; M183); T123/T127 сохраняют вход «ни полной таблицы ps, ни /proc»: в измеряемой остановке без снимка запомненные проверяются `/proc` → членство в своём scope → одиночный ps (кроме E3), новорождённые без снимка не достигаются до `cgroup_kill` конца окна — без дерева помощники ловушки неотличимы. `RUNLIMITS_TEST_SCOPE_UNREADABLE=1` отказывает только чтению `scope_pids()` (T123s). Ручка `RUNLIMITS_TEST_START_UNREADABLE` действует и в `/proc` (T66, T129);
- путь «ушёл родитель → TERM в окне остановки» общий для площадок: T120 идёт на обеих, darwin-нога не измерена;
- пересылка INT и отсчёт «рождённых после» от неё — код общий для площадок (`forward_pending`, щажение хоста без условия площадки при живом снимке): T128 идёт на обеих, darwin-нога не измерена.
